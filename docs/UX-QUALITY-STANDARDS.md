# 家庭記帳系統｜整體 UX 品質標準

本文件將家庭記帳系統的共同使用體驗標準固定在專案內，供後續功能開發、介面調整及驗收使用。所有新功能及重構都應遵循本文件；既有財務規則、權限及資料安全優先於視覺調整。

## 1. 產品目標

讓不熟悉記帳系統的家庭成員，包括長輩，拿起手機便能理解目前位置、知道下一步，並安心完成日常記帳。

設計優先順序：

1. 正確、安全、穩定。
2. 常用操作簡單、快速、不遺失資料。
3. 手機、平板、桌面都容易操作。
4. 視覺一致、清楚、舒適。
5. 裝飾與動畫最後考慮，不得妨礙操作或效能。

## 2. 全系統共通互動規則

- 每個可操作控制項都必須有明確用途、可理解標籤及操作回饋。
- 儲存、載入、成功、失敗、空資料及權限不足都要有清楚狀態。
- 會等待的動作必須有合理結束條件；不得無限顯示「處理中」或只讓畫面空白。
- 失敗時保留使用者已輸入的資料；切換工作區不得無故清除未儲存內容。
- 危險操作與一般操作視覺區分；作廢、刪除、完成對帳等重要操作必須說明影響。
- 不可出現看似可按卻沒有作用的控制項。不可用只有顏色的方式傳達狀態。
- 提示使用一般家庭成員能理解的繁體中文，說明目前狀態及可執行的下一步。

## 3. 視覺及表單

- 按鈕、欄位、卡片、狀態訊息、表格及導覽應沿用共用樣式，不要每個模組自行發明不同互動方式。
- 層級清楚：頁面標題、區塊標題、欄位標籤、內容、輔助說明各有清楚區分。
- 重要金額及狀態應易於辨識；日期統一使用 YYYY-MM-DD；不同幣別分開顯示與計算。
- 必填／選填欄位清楚；placeholder 不得取代欄位標籤。
- 金額、日期、數字欄位應使用適合的輸入型態及手機鍵盤。
- 欄位驗證錯誤應靠近欄位呈現，並保留已輸入內容。
- 文字不得截斷、重疊、亂碼；正文與提示文字應有足夠對比。

### 色彩與視覺氛圍

- 全站以暖白／柔和米白為基底，搭配淺藍、寶藍、柔和玉綠與香檳金，形成清爽、明亮且有質感的家庭財務視覺。
- 寶藍作為主要操作、目前選取及鍵盤焦點色；淺藍用於次要操作、篩選區與資訊層次；柔和玉綠用於收入、成功狀態與溫和的輔助區塊；香檳金只作為細節、邊框、圖表點綴與少量視覺亮點。
- 卡片及表單維持暖白表面，利用淡藍灰邊框、玉綠輔助底色及柔和陰影建立層次；避免四種顏色平均鋪滿，也避免高飽和色大面積覆蓋背景。
- 主要按鈕使用足夠深的寶藍底與白字；次要操作使用淺藍底與深藍字；收入／成功使用玉綠，支出、警告與錯誤保留清楚不同的語意色，不可只靠顏色辨識。
- 香檳金不得用於小尺寸正文或白底上的低對比文字；需要文字時使用足夠深的金棕色。文字、提示、輸入框、焦點外框及禁用狀態須保持清楚可讀；保留鍵盤焦點與觸控狀態。
- 相機掃描器可維持深色取景區，確保相機預覽對比與辨識操作，不需為了全站暖色而犧牲辨識效果。

## 4. 裝置與 RWD

### 手機
- 以單欄、卡片、清楚分段為優先；主要按鈕要容易點擊。
- 不應要求左右滑動才能看到主要欄位或完成主要操作。
- 寬表格可保留水平捲動，但必須有清楚的區塊標題、捲動提示及不被截斷的關鍵資訊；優先評估改為卡片或欄位收合。
- 底部導覽與固定操作列不得遮住表單、通知或內容。
- 表單控制項字體及觸控範圍需適合觸控，避免誤觸。

### 平板
- 依實際寬度自動調整欄位、卡片及欄數；橫向可利用空間，直向仍需完整操作。
- 不應強制固定左右分割，或要求旋轉裝置才能完成任務。

### 桌面
- 善用寬度展示資料；避免內容過窄或不必要的空白。
- 表格、篩選器及多欄表單應對齊、易比較及易閱讀。

## 5. 導覽與資訊架構

- 常用功能應容易抵達；低頻管理功能依清楚分類收納及搜尋。
- 導覽標示目前所在功能；進入子頁面後，返回／收起方式一致且容易找到。
- 使用者沒有權限的功能應依既有權限模型隱藏或呈現明確說明。
- 切換家庭時要清楚顯示目前家庭，並重新套用該家庭的權限。
- 保留現有 permission-aware navigation；前端隱藏不能取代後端授權。

## 6. 發票與收據掃描的專屬標準

- 電子發票優先使用全畫面自動尋找 QR Code，不強制左右框或固定角度。
- 發票基本資料 QR 是日期、金額及發票號碼的主要來源；商品明細 QR 是選配資訊，不得阻擋基本記帳。
- 只讀到商品明細時，需提示尚未取得基本資料並提供拍照／重新辨識等下一步；不得無限等待。
- 拍照應優先擷取網頁目前已開啟的相機畫面，避免不必要的原生相機 App 切換及頁面重載。
- 拍照後立即顯示回饋、照片預覽及辨識狀態；QR 解碼失敗仍保留影像，繼續本機 OCR 或人工核對。
- QR 解碼及 OCR 優先在使用者裝置執行；未經同意不得上傳照片或呼叫付費 OCR API。
- 辨識結果只作為待核對欄位；必須由使用者確認後帶入記帳表單，不能自動建立正式交易。
- 不確定的欄位應留空或標示待確認，不得把猜測值當成事實。

## 7. 帳務、資料及權限不可破壞的邊界

- 帳單、付款、收入、支出、轉帳及信用卡負債的資料模型與計算關係不得因 UI 優化而改變。
- 銀行匯入原始明細與家庭正式交易分離；對帳配對及差異分類不得擅自改寫銀行原始資料或建立重複交易。
- 作廢須保留歷史及稽核紀錄；不得以 UI 改善為由硬刪除正式帳務資料。
- 多幣別分開計算，除非有明確匯率與換算依據。
- 角色、細項權限、資料範圍及家庭隔離維持後端強制驗證。
- 任何可能改變資料結構或正式帳務結果的修改，需有遷移策略、回歸測試及可追溯說明。

## 8. 工程及驗收流程

1. 先檢查 main 分支最新程式與實際測試，不依賴舊分支或過期描述。
2. 找出可重現的根因，再改程式；避免只調整表面文案或參數。
3. 優先抽出共用元件及樣式；每次修改聚焦一組可驗收的問題。
4. 新增／更新自動化測試，涵蓋成功、失敗、權限、資料保留及 RWD 基礎。
5. 經 GitHub Pull Request 與 CI，所有必要檢查通過後才合併。
6. 確認 Render 部署為 Live，並檢查健康狀態及近期錯誤日誌。
7. 分開回報：自動化測試通過、正式部署 Live、實際裝置驗收通過。
8. 相機、檔案選擇、觸控、螢幕旋轉等依賴裝置的功能，必須保留實機驗收項目；不能只用程式測試宣稱修好。

## 9. 每次功能交付摘要

每個 PR／版本都應清楚列出：
- 解決的使用者問題及根因。
- 改動頁面／流程及沒有改動的帳務邊界。
- 新增或更新的自動化測試。
- CI 結果、合併 commit、Render deploy ID 及 Live 狀態。
- 尚需使用者實機驗收的項目。
